# CP Engine Spec v02 — Proposed Architectural Change

> Single change to v01: split the protocol from the corpus, support multiple tenants. Same vocabulary, same modes, same sync semantics — different physical layout. Drafted while brainstorming where Drew's wider repo set (Python directory: ~70 repos across FPSF and Canonic) fits into the system. Tony — please review and either accept, push back, or refactor.

## Why this surfaced

v01 (and the three accepted amendments) describe a single `context-protocol` repo holding one master CP, one weekly CP, and a `projects/` directory. That works for MC-2's project list. It does not work for the rest of Drew's working surface:

- **First Person internal tooling** — `mc-2` itself, plus `1p-webflow-builder`, `1p-component-library`, `1p-dashboard`, `1p-project-utilities`, `1p-code-agent`, `fathom-meeting-sync`, `hex-brand-zoner`, etc. ~10 repos that *run* FPSF, distinct from the client jobs the engine was first scoped for.
- **Canonic / personal work** — `storyos` (and variants), `unf-forge`, `canonic-website`, etc. ~20 repos that aren't FPSF concerns at all.

Three options were considered:

1. **One repo, more projects** — drop everything into `context-protocol`. Rejected: forces every consumer to load every repo, or requires inventing `is_drew_only` next to `is_internal`.
2. **Separate repos, copy the framework** — what we'd get by default. Rejected: every script change in one place has to be propagated to two others by hand. Drift guaranteed within a quarter.
3. **Separate repos, shared framework** — the engine becomes a versioned package; each tenant's CP corpus is a thin repo that depends on it.

Option 3 is the proposal.

## The change in one paragraph

Split today's `context-protocol` repo into **two kinds of artifacts**: one **framework package** (`cp-engine`) holding the spec, sync code, renderers, and CLI; and **N tenant repos** (`cp-1p`, `cp-firstpersonsf`, `cp-canonic`), each holding only that tenant's CP files and a config pointing at its tracked project repos. Tenants depend on the framework via `pip install cp-engine` and a pinned semver. Framework updates flow one direction: cut a release, bump the pin, every tenant gets the change. No copy-paste.

## Tenants

Three on day one:

| Tenant | What it tracks | Visible to |
|---|---|---|
| `cp-1p` | First Person *jobs* (client engagements). Project codes like `ggl-5168`, `ibx-5153`, `pph-5182`. | Drew, Tony, Brandon, Marcello |
| `cp-firstpersonsf` | First Person *internal* tooling and components. Includes `mc-2` itself as a tracked project. | Drew, Tony |
| `cp-canonic` | Canonic / personal repos (`storyos`, `hex-brand-zoner`, etc.). | Drew, Tony, Brandon, Marcello |

`mc-2` lives inside `cp-firstpersonsf` as a normal project (one CP file). It is a bigger initiative than most FPSF tools, but we're not introducing an `initiative/` concept on day one — promote it later if a second one appears. (YAGNI applied here deliberately.)

Visibility is enforced by GitHub repo permissions, not by the engine. Each `cp-*` is a private repo with an explicit collaborator list.

## Framework / tenant boundary

What `cp-engine` owns:

- The spec (v02.md and forward), including all v01 amendments as folded text
- Sync logic: GitHub Issues → engine-managed regions of project CPs
- Renderers: `master-cp.md`, `weekly-cp.md`, `CLAUDE.md`, `projects/<code>.md` (Jinja templates)
- Status helpers: `isActiveStatus`, vocab constants, active-subset filter
- Mode loader: which files mode 1/2/3/4 reads, the no-auto-globbing enforcement
- The `cp` CLI: `cp init`, `cp sync`, `cp render`, `cp status`
- A reusable GitHub Action (`cp-engine/sync@v0`) tenants drop into their workflows

What each tenant repo owns:

- `.cp-engine.toml` — committed config: tenant name, project list, GitHub coordinates per project
- `.cp-engine.local.toml` — gitignored, per-machine: where each project repo lives on this machine
- `master-cp.md`, `weekly-cp.md`, `projects/*.md` — committed CP files, mix of generated regions and hand-written content
- `CLAUDE.md` — fully generated by the engine. **No hand-edits.** A `CLAUDE.md` change is a `cp-engine` change.
- `.github/workflows/sync.yml` — invokes the `cp-engine/sync` Action on cron

Critical rule: **tenants never fork engine code.** If a tenant needs new behavior, the path is "open an issue against `cp-engine`, ship a versioned change, bump the pin." Copy-paste is prohibited; that's the entire point of the split.

## Per-machine repo paths

Project repos live in different places on different machines (Drew's `~/Documents/Python/`, Tony's elsewhere, Dropbox-symlinked working dirs are common). Path config is split:

```toml
# .cp-engine.toml  (committed)
[[projects]]
name = "storyos"
github = "CanonicOS/storyos"

# .cp-engine.local.toml  (gitignored)
[repos]
storyos = "~/Documents/Python/storyos"
```

The committed file is the source of truth for *which projects exist*; the local file is the source of truth for *where they live on this machine*. `cp init` walks new collaborators through populating the local file the first time. Engine resolves symlinks at read time so Dropbox-backed working dirs Just Work.

The engine fails loudly when a project is in `.cp-engine.toml` but missing from `.cp-engine.local.toml` — silent skipping is the kind of thing that bites three weeks later.

## Sync — what runs where

Sync is **automated, not user-triggered.** A GitHub Action in each tenant repo runs `cp-engine/sync@v0` on cron (hourly), authenticated with a tenant-scoped PAT or GitHub App with cross-org read access. The action:

1. Reads GitHub Issues from each tracked project's source repo
2. Filters to active subset (`is_active_status(mc_status)` AND `is_internal=false`)
3. Reconciles into engine-managed regions of project CPs
4. Re-renders `master-cp.md`, `weekly-cp.md`, `CLAUDE.md`
5. Pushes to a `cp-sync` branch with a bot identity (`cp-engine-bot[bot]`); auto-merges to `main` if checks pass

`cp sync` also runs locally for "I just changed something, render now" cases. Same Python module — not a re-implementation.

## Engine-managed regions

Project CPs mix generated and hand-written content. The engine writes only between HTML-comment markers:

```markdown
<!-- cp-engine:start tracked-issues -->
| # | Title | Status | Owner | Updated |
|---|-------|--------|-------|---------|
| #42 | Auth bug | Open | drew | 2026-05-06 |
<!-- cp-engine:end tracked-issues -->

## Notes (hand-written, engine never touches)

The auth bug is blocked on Brandon's API change...
```

Outside the markers is sacred. This is the same pattern used by codegen tools and is robust against round-trips.

## Loading mechanics across the two surfaces

**Claude Code (local):** session opens in a tenant repo or a project repo. With local FS access, it can load project source on explicit user request. Mode 1-4 from v01 still apply, scoped to the tenant repo it's in.

**Claude desktop app:** session connects to a tenant repo via the official GitHub MCP (or `gh` — the engine doesn't care which). Reads CP files directly from GitHub. **Cannot read project source code** unless those repos are also GitHub-MCP-connected. **Cannot run sync** — that's why sync is automated.

Bottom line: the corpus is the same across both surfaces; only the loading mechanics differ. The cases that require local source (e.g. "look at `storyos/api/auth.py`") naturally belong in Claude Code anyway.

### Co-loaded tenants in a single session

A given user often spans more than one tenant in their daily flow. Brandon and Marcello, for example, work across both `cp-1p` (client engagements they staff) and `cp-canonic` (Canonic internal). Their normal pattern is connecting both tenant repos to the desktop app's GitHub MCP and letting the conversation determine which one Claude reads.

This co-loading is supported, with one rule: the **gatekeeper rule from v01 Amendment 2** ("no auto-globbing outside this repo") must be phrased relative to the *set of currently connected tenant repos*, not the single repo the session was opened in. The generated `CLAUDE.md` will read approximately:

> Do NOT auto-glob, read, or search any path outside the connected tenant
> repositories unless the user explicitly references it by path or name.

Project repos remain opt-in regardless of how many tenants are connected. Connecting two tenants does not implicitly load 70 project repos.

## Migration path

Today's `context-protocol` repo becomes `cp-engine` (the framework). Spec docs stay; project-CP files (none yet) don't need migration. PR #17 in MC-2 keeps moving — the helper and refactors land on schedule. Once `cp-engine` v0.1 is released:

1. Create `cp-firstpersonsf` from a fresh template; seed `projects/mc-2.md` from the existing MC-2 state
2. Create `cp-1p`; seed projects from current MC-2 active jobs
3. Create `cp-canonic`; seed empty, populate over the next few sessions

No git history is destroyed — the framework keeps its history, tenant repos start fresh.
